# In-Chat Mini-Game Development Skill (ST-TwoMoreThings)

本指南总结了在虚拟手机短信插件（ST-TwoMoreThings）中开发与 AI 角色对弈的小游戏（以抽鬼牌 Old Maid 为标准范例）的完整工程规范、提示词设计哲学与避坑准则。

---

## 核心设计哲学 (Core Philosophies)

### 1. 玩家主体性与“零代打”原则（Zero Ghostwriting）
* **严禁程序代发玩家对话**：绝不要在玩家点击“接受”、“更换赌注”、“拒绝”、“催促”等按钮时，用代码拼凑一段玩家台词并以玩家身份发送到对话流中。
  * *原因*：用户拥有独立的性格、语气、OC 设定或语种习惯，生硬代发会严重出戏并剥夺玩家自由度。
* **以「系统事件消息」记录交互**：所有的按钮操作（如接受、加码、结算）均生成轻量的灰色系统动作消息（`role: 'system', type: 'game-action'`），客观记录对弈事实。
* **输入框始终留给玩家**：短信输入框完全由玩家自主掌控，玩家想在何时说何话、表达何种情绪，全凭自主输入。

### 2. 仿真实私聊与“纯对话”规范（Pure Dialogue）
* **严禁括号动作与小说式旁白**：在短信界面中，严禁在角色对话正文中出现 `（把手中的牌放在桌上）`、`（眼神闪躲）` 等小说旁白。
* **情绪线上化表达**：引导角色通过线上打字习惯（短句、标点、emoji、语气词、错字秒撤回等）展现对弈中的心虚、得意或挑衅。
* **边玩边聊，拒绝纯对弈机器**：不要搞“打牌中禁止闲聊”的设定。游戏是角色互动的催化剂，角色应一边打牌一边聊日常、互相吐槽。

### 3. 数据与提示词程序化绑定（Programmatic Truth）
* 所有的博弈参数（如赌注 wager、轮次 round、胜负 winner）必须在程序数据模型中真实存在，绝不依靠纯口头约定。
* 双方（玩家与 AI）均可发起、协商、修改参数，界面与上下文双向同步。

### 4. 战局生命周期闭环与上下文减负（Context Hygiene）
* **战局提示词按需注入**：游戏专用的动态态势 Prompt 必须严格绑定游戏状态（如 `game.status === 'playing'`），对决未开始或已结束时立即彻底停止注入，切忌常态污染正常私聊上下文。
* **终局过渡缓冲带（5 轮滑动窗口）**：游戏结束后，若立即清除全部过程播报，角色会瞬间“失忆”无法调侃胜负；若永久保留，则会持续侵占上下文 Token。规范采用“5 轮过渡缓冲”：终局后保留 5 轮 AI 回复的播报注入，第 6 轮起自动清除历史动作流水，实现上下文平滑释放。

### 5. 先手真实性与自动无缝唤醒（Starter Dynamics）
* **打破固定先手惯性**：开局支持 50% 抛硬币随机判定先手（`starter: 'random'`）；弹药/牌库打空换轮时，按轮次奇偶（`round % 2`）交替换先手，保持博弈紧张感与公平性。
* **AI 先手无缝出招**：掷硬币判定为 AI 先手时，底层在接受对决后直接激活 AI 行动逻辑并自动触发续写开局（`service.continueChat`），无需用户多余点击。

## 架构五层模型 (Five-Layer Architecture)

```
┌────────────────────────────────────────────────────────┐
│ 1. 独立规则引擎 (src/games/<game>.js)                   │  纯函数状态机：发牌、行棋、判定、胜负
├────────────────────────────────────────────────────────┤
│ 2. 数据存储与消息模型 (src/store.js & src/content.js)   │  type: 'game' 卡片 + type: 'game-action' 系统流
├────────────────────────────────────────────────────────┤
│ 3. 浮动对弈抽屉 (src/ui/game-board.js & style.css)     │  独立弹层：牌桌/棋盘交互、参数修改、防遮挡输入框
├────────────────────────────────────────────────────────┤
│ 4. 提示词与时序治理 (src/prompts.js & src/content.js)   │  独立宏插槽、结构化动作契约、解决陈旧用户发言陷阱
├────────────────────────────────────────────────────────┤
│ 5. 消息调度与全自动交互 (src/messages.js & src/ui.js)   │  玩家行动后自动唤醒 AI 出牌与回话，无缝对决
└────────────────────────────────────────────────────────┘
```

## 阶段开发标准流程 (Step-by-Step Runbook)

### 第一阶段：设计数据模型与纯规则引擎
在 `src/games/<game-id>.js` 编写确定性逻辑：
1. **定义状态结构**：
   ```javascript
   {
     kind: 'game_name',
     gameId: '...',
     status: 'invited' | 'countered' | 'playing' | 'finished' | 'rejected',
     wager: '赌注或规则参数',
     turn: 'user' | 'ai',
     round: 1,
     winner: '',
     loser: '',
     lastAction: { type: '...', actor: '...', description: '...' },
     history: [],
     state: { ...游戏专属手牌/棋盘状态... }
   }
   ```
2. **编写纯函数**：
   - `create<Game>Invitation({ sender, wager, ... })`
   - `accept<Game>(gameState, { ... })`
   - `userMove(gameState, actionParams)`
   - `aiMove(gameState, actionParams)`
   - 保证所有状态更新通过深度克隆返回新对象，无外部副作用。

### 第二阶段：提示词契约与宏定义
在 `src/prompts.js` 和 `src/preset-engine.js` 注册独立宏（如 `{{old_maid_prompt}}`）：
1. **规则说明**：简明扼要说明规则与输赢判定。
2. **主动发起与响应规范**：角色想玩时发卡片 `{"type":"game","game":{"kind":"...","action":"invite","wager":"..."}}`；收到邀请时在正文回应并在顶层输出 `{"gameAction":"accept"}` 或 `{"gameAction":"counter","wager":"..."}`。
3. **回合动作指令契约（Action Contract）**：
   ```json
   {
     "gameAction": {
       "action": "move_type",
       "moveIndex": 0,
       "wager": "可选加码或改注",
       "notice": "【角色名】动作生动描写【玩家名】……"
     }
   }
   ```
4. **纯对话约束**：明确要求 `messages[].text` 不得带括号动作描写，由 `notice` 承担系统播报。

### 第三阶段：时序治理（防止陈旧输入陷阱）
在 `src/content.js` 的 `extractLatestUserInput` 中必须治理轮流对弈时序：
* **核心陷阱**：玩家开局说了“好，开始打牌”，后续 10 轮都是摸牌与 AI 回话。若只倒序查找最后一条 user 消息，AI 每轮都会收到 `[用户最新发言：好，开始打牌]`。
* **治理逻辑**：
  ```javascript
  if (lastAssistantIdx !== -1 && lastAssistantIdx > lastUserIdx) {
    if (activeGame || hasRecentGameAction) {
      return '[小游戏对弈推进] 玩家已完成操作，当前轮到你推进对局并发表日常台词。';
    }
    return ''; // 普通对话返回空，预设引擎会自动剥离用户发言插槽
  }
  ```

### 第四阶段：交互界面与卡片
1. **邀约卡（`src/ui/cards.js`）**：
   - 包含状态药丸（等待回应 / 协商中 / 进行中 / 已结算）。
   - 动作按钮：接受、更换赌注、拒绝、进入对弈桌。
2. **抽屉面板（`src/ui/game-board.js`）**：
   - 放置在屏幕上方或抽屉内，绝对不能遮挡底部的 `#sms-draft` 聊天输入框。
   - 顶栏显示动态轮次与可点击修改的参数药丸（`data-action="edit-game-wager"`）。
   - 终局结算提供清晰的胜负横幅与系统提醒按钮。

## UI 与交互规范 (UI & Interaction Standards)

在手机短信聊天这一受限视口（Viewport）内开发对弈交互，必须严格遵循以下 UI 准则，确保无论在桌面端还是移动端窄屏下，均具备极致丝滑、符合移动端人体工学的操作体验：

### 1. 视口防遮挡与全时打字可用（Anti-Occlusion & Unblocked Typing）
* **严禁遮挡底部输入框**：
  * 对弈抽屉（Game Board Drawer）必须定位在对话视图中上部，其高度通过 `max-height: calc(100% - 140px)` 或固定百分比严格限制，内部内容独立纵向滚动（`overscroll-behavior: contain`）。
  * 无论是对弈进行中还是终局结算状态，底部的 `#sms-draft` 聊天输入框、发送按钮、表情与附件图标必须 100% 完全暴露并随时可点击打字。
* **背景半透沉浸感**：
  * 抽屉展开时，背景对话流保持半透或可见状态，不要使用纯黑全屏遮罩把对话彻底阻断，保持“在聊天中切出小桌子对局”的场景沉浸感。

### 2. 双态折叠、可交互图标与顶部悬浮胶囊（Dual-State Drawer & Interactive Icons）
* **游戏图标做成可交互功能按键**：
  * 抽屉顶栏的小游戏图标严禁作为干瘪的静态图案，必须实现为可点击按键（`button.game-title-icon-btn`）；
  * 点击该图标即可就地呼出或切换“玩法教程/道具机制说明弹层”（详细展示各道具效果、判定规则），随时随地可供玩家查阅规则与战术道具。
* **道具与游戏图标风格一致性**：
  * **严禁滥用系统彩色 Emoji**：严禁直接在道具栏或操作控件中插入 🔍、🪚、🍺、⛓️、🚬 等五颜六色的系统 Emoji；
  * **统一单色线性 SVG 规范**：所有小游戏道具（放大镜、手锯、啤酒、手铐、香烟等）必须全部设计或引入与本插件全局保持完全一致的单色线性 SVG 图标（统一 stroke 粗细、圆角及主题配色 `currentColor`），保持高级统一的 UI 质感。
* **无缝折叠交互与悬浮胶囊**：
  * 抽屉顶栏右上角必须常驻折叠按钮（`fold-game-board`，使用 `icon('arrow-down')` 或 `icon('close')`）；
  * 折叠后，主屏自动转为顶部优雅的悬浮小药丸（`button.game-floating-pill`，高度 28~32px），内嵌单色线性游戏图标、纯数字轮次（`X 轮`）、比分血量及当前行动方呼吸点，点击秒级重开，不遮挡联系人导航栏与底部打字区。

### 3. 极简去噪与“零括号解释”规范（Text Minimalism & Zero Parenthesis Clutter）
在受限视口中，文字的极简化是维持高质感 UI 的核心生命线：
* **严禁给人名/角色添加括号备注**：
  * 界面文案与战局播报中，坚决杜绝带有括号说明的人名备注，如 `【<user>】(旅行者)`、`【角色】(Seraphina)`、`你(玩家)`；
  * 硬编码文本一律直接书写 `<user>` 与 `角色`；
  * 动态填充文本一律直接呈现实际姓名（如 `<user>` 或 `Seraphina`），绝不加括号注释。
* **删除操作与道具下的一切冗余副文案**：
  * 坚决删除在道具与操作按钮下的辅助解释小字（如“实弹伤害空弹虚惊”、“点击立即使用”、“锯短枪管伤害翻倍”等全部删除）；
  * 控件界面保持极致克制，只保留道具图标、核心名称与数量，具体效果由点击游戏图标唤起的教程页负责。
* **纯中文选项，拒绝冗余英文翻译**：
  * 小游戏选择入口、菜单按钮直接使用纯中文（如 `恶魔轮盘`、`抽鬼牌`），严禁加上冗余的英文副标题（如拒绝 `恶魔轮盘 Buckshot Roulette`）。
* **纯数字轮次**：
  * 顶栏及胶囊中轮次直接简写为纯数字格式 `X 轮`（如 `1 轮`、`2 轮`），而非冗长拖沓的 `恶魔轮盘 · 第 1 轮`。
* **终局折叠收纳条文案极简化**：
  * 终局收拢条文案严格限定为 `恶魔轮盘对决结束 ▾`，拒绝“点击展开复盘”、“共击发X次”等啰嗦提示。

### 4. 顶栏单行横排与文本溢出截断（Top Bar Layout & Text Truncation）
* **严格单行横向排布**：
  * 抽屉顶栏的元素必须保持紧凑的单行水平对齐（`display: flex; flex-direction: row; align-items: center; justify-content: space-between;`）；
  * 必须确保 `X 轮` 标签、中间赌注药丸、右侧认输/关闭按钮位于同一水平线，严禁因内容换行撑大顶栏高度。
* **超长赌注省略号截断保护**：
  * 赌注药丸限制最大宽度（`max-width`），默认只展示前几个字，超长文本强制使用 CSS 省略号隐藏（`text-overflow: ellipsis; white-space: nowrap; overflow: hidden;`）；
  * 玩家若想看全长赌注，点击药丸唤出设置弹窗即可查看和编辑完整内容。

### 5. 邀约卡与结算卡结构规范（Invitation & Settlement Card Architecture）
卡片（`type: 'game'`）采用清晰的三段式卡片布局：
```
┌────────────────────────────────────────────────────────┐
│ Header:  [图标] 恶魔轮盘              [状态药丸: 进行中] │
├────────────────────────────────────────────────────────┤
│ Body:    赌注: [ 纯娱乐 ✎ ]                            │
│          双方初始体力: 3点 | 包含道具箱                 │
├────────────────────────────────────────────────────────┤
│ Actions: [ 进入对战桌 (主要) ]     [ 退出/认输 (次要) ]  │
└────────────────────────────────────────────────────────┘
```
* **状态药丸（Status Badge）语义化**：
  * `invited`（等待回应 / 待确认）：浅蓝/中性灰底色。
  * `countered`（协商改注中）：浅橙/警告色。
  * `playing`（对决进行中）：主题激活色（`var(--pp-active)`）。
  * `finished`（对决完结）：静默灰底。
  * `rejected`（已谢绝）：半透明弱化。
* **开局卡与结算卡解耦原则**：
  * **开局卡保持静态**：开局卡只在被接受时生成一张静态事实卡（记录开始与初始赌注），严禁在后续对决推进中随着每一枪/出牌去修改历史开局卡文本，避免历史上下文发生反复重写与不可逆变动。
  * **终局独立结算卡**：分出胜负时，由终局触发方或底层额外派发一张独立的【终局结算卡】（注明对决结束、最终胜者 `<user>` 或角色），形成清晰完整的起止闭环。

### 6. 对战流消息与终局折叠收纳条（Stream Actions & Post-Game Folding Capsule）
* **过程动作通知药丸（`game-action-notice`）**：
  * 居中弱化展示，采用极简圆角灰底胶囊样式（`background: var(--pp-surface-soft)`），字号微缩（`10.5px ~ 11px`），文字客观精炼交代动作。
  * **渐显删除按钮（`system-notice-delete`）**：默认 `opacity: 0`，仅在鼠标悬停（hover）或移动端触控激活时淡入，支持用户自主清理流水，严禁使用破坏排版的大红叉或显眼按键。
* **终局折叠收纳胶囊（Post-Game Folding Capsule）**：
  * 游戏结束后，连续的多条 `type: 'game-action'` 消息在 UI 上自动聚合收拢在单个折叠条后；
  * **文案规范**：文案统一为 `【恶魔轮盘对决结束 ▾】`，配以单色折叠/展开指示图标（`icon('down')` / `icon('next')`）；
  * **展开/收起平滑过渡**：点击折叠条可随时展开查看该局历史出招流水，再次点击即收拢，既保持主聊天流清爽整洁，又完全保留复盘追溯能力。

### 7. 对弈桌战场布局与对峙视区（Arena Layout & Turn Indicators）
在抽屉内部，采用上下对峙式战场布局：
* **上方：AI 角色态势区**（角色头像/名称、血量指示槽、手牌/剩余道具栏、状态标签）。
* **中央：公共对峙/牌桌区**（如恶魔轮盘的霰弹枪弹仓视区、抽鬼牌的公共出牌弃牌堆、当前轮次信息）。
* **下方：玩家操作态势区**（玩家血量指示槽、玩家可用手牌/道具栏、核心行动按钮）。
* **生命指示槽（HP Pip Display）**：
  * 抛弃传统粗笨进度条，采用轻巧的胶囊点阵或圆点序列（Pip 表示法）；
  * 满血呈现饱满实心色，扣血呈现空心描边或半透虚线，扣至 1 点濒危时呈现呼吸告警色。
* **道具栏与手牌区（Item & Hand Grids）**：
  * 横向滚动陈列（`overflow-x: auto; overscroll-behavior: contain; scrollbar-width: none;`）；
  * 单个道具展示图标、名称与剩余数量；
  * 可用时高亮浮起，非己方回合或条件不满足时置灰并设置 `pointer-events: none; opacity: 0.45;`，杜绝非法误触。
* **回合行动锁与防连击保护（Turn Action Lock）**：
  * 当轮到 AI 行动时，玩家侧的核心行动按钮（如“向对方开火”、“向自己开火”）必须彻底禁用（`disabled`），并呈现 `[对方行动中...]` 或加载中呼吸态，明确告诉用户当前为等待状态，防止用户快速连点或破坏状态机。

### 8. 动态参数交互与原生弹窗（Interactive Pills & Modal Formats）
* **局内可交互药丸**：
  * 赌注等参数在顶栏与结算横幅中展示为交互按钮（`button.game-wager-pill.is-clickable`，附带 `✎` 铅笔图标标记）。
  * 悬浮带有轻微缩放反馈（`transform: scale(1.02)`），提示可点击。
* **使用插件原生风格弹窗（`dialog.custom`）**：
  * 点击时呼出原生轻量弹窗，提供输入框、快捷预设选项标签、确认与取消按钮；
  * 严禁直接使用浏览器原生的粗暴阻断式 `window.prompt()` 或 `window.confirm()`；
  * 弹窗必须支持 `Esc` 键快捷退出、`Enter` 键快速提交，焦点自动落在输入框。

### 9. 触控工学与响应式适配（Touch Ergonomics & Responsive UX）
* **触控热区尺寸**：所有可点击控件（按钮、卡牌、道具格、折叠图标）的触控热区最小不低于 36×36px，防止移动端误触。
* **卡牌重叠与悬浮手感**：
  * 扇形手牌（`cards-fan`）采用负边距重叠展示，支持触摸/悬停上浮微动（`translateY(-10px) scale(1.06)`）与阴影加深（`box-shadow: 0 8px 16px rgba(0,0,0,0.12)`）。
* **严防文本选中误触**：
  * 对弈抽屉、卡牌、操作按钮、道具格子等全量配置 `user-select: none; -webkit-user-select: none;`，彻底避免用户在双击、快连点或拖拽手势时触发浏览器默认的蓝色文本高亮或系统复制菜单。

### 10. 设计系统主题变量与色彩语义（Design Tokens & Semantic Color Palette）
* **严禁硬编码色值**：
  * 全量界面样式必须严格使用项目的全局 CSS 变量（`var(--pp-*)`），自适应插件自带的浅色、深色及自定义主题：
    - 面板底色：`var(--pp-surface)` 与 `var(--pp-paper)`；
    - 弱化背景：`var(--pp-surface-soft)`；
    - 分割线与描边：`var(--pp-rule)` 与 `var(--pp-divider-soft)`；
    - 正文字色：`var(--pp-ink)`；
    - 弱化说明字色：`var(--pp-muted)`；
    - 品牌激活色：`var(--pp-active)`。
* **语义化对战色彩规范**：
  * **回合指示**：玩家行动回合高亮主题激活色（`var(--pp-active)`）；对方行动回合呈现静默灰（`var(--pp-muted)`）。
  * **终局胜负**：
    - 玩家胜利横幅：浅绿底绿字（`background: #e6f4ea; color: #137333; border-color: #ceead6;`）；
    - 玩家失败横幅：浅红底红字（`background: #fce8e6; color: #c5221f; border-color: #fad2cf;`）。
  * **弹药与危险标识**：实弹采用警示红（`#d93025`），空弹采用安全蓝/浅灰（`#1a73e8` / `#5f6368`）。
* **严禁彩色系统 Emoji 污染图标系统**：
  * 界面按钮、状态指示和系统流水中严禁使用操作系统原生的彩色 Emoji（如 🎲、🃏、🔫）；
  * 全面统一调用系统自带的单色线性 SVG 图标系统（如 `icon('gamepad')`、`icon('edit')`、`icon('down')` 等），保持极简优雅的高级感。

## 常见问题与避坑解决方案（实战案例沉淀）(Troubleshooting & Battle-Tested Solutions)

在恶魔轮盘（Buckshot Roulette）等博弈小游戏的实装过程中，总结出的高频问题与最佳解决方案如下：

### 1. 终局后上下文膨胀与 Token 占用问题
* **问题表象**：
  游戏结束后回到正常聊天，但对战流水（击发、道具使用、重装弹药等系统播报）持续累积在聊天上下文中，随对话深入持续消耗巨额 Token。如果立刻在终局时全量抹除，AI 角色又会瞬间“失忆”，无法顺畅地就刚结束的战况调侃、兑现赌注或发表感言。
* **解决方案：5 轮滑动窗口过渡缓冲 + 自动清除**：
  - **终局 5 轮缓冲带**：记录游戏结束时的最新消息索引（`finishMessageIndex`）。在游戏结束后的 **前 5 次 AI 回复轮次**（以 AI 生成次数为准，而非消息绝对条数），这些对战播报仍然注入到 Prompt 中，使角色能自然承接胜负话题；
  - **第 6 轮起自动释放**：超过 5 轮后，过滤器（如 `filterFinishedGameActions`）将这些历史动作播报从给主模型的上下文构建中静默剥离，彻底释放 Token；
  - **界面与数据解耦**：UI 层面在终局后第一时间收纳为折叠条，不干扰聊天视觉，与底层的 Prompt 缓冲带各自独立生效。

### 2. 回合混淆与“抢枪/代打”问题
* **问题表象**：
  模型在提示词中分不清当前究竟是谁的回合，经常出现“明明轮到玩家开枪，AI 却在回复中替玩家开火”或者“AI 自称玩家，开枪打自己/打对手逻辑错位”。
* **解决方案：客观标签体系 + 分支指令硬隔离**：
  - **消除代词与人名括号**：严禁在提示词中使用“你”、“对方”、“玩家”等具有双向歧义的词汇，坚决不加人名括号备注（如 `爱丽丝(角色)`）。直接统一采用客观规范的标识：`【<user>】` 和 `【角色】`；
  - **严格根据底层回合归属动态分流 Prompt 指令**：
    - **当轮到 AI 时**：明确要求必须在 JSON 顶层返回结构化动作指令（如 `shoot_opponent` / `shoot_self`），并在聊天气泡中配合出招台词；
    - **当轮到 `<user>` 时**：**明确下达禁令**，严禁模型替 `<user>` 做任何对弈操作或开枪决策，限定模型只能发送纯日常/催促台词，等待 `<user>` 自主操作。

### 3. 战局 Prompt 冗长失焦问题
* **问题表象**：
  将整个对决的完整历史记录、每一发开枪明细全部拼入 Prompt，导致每次注入内容长达数十行，模型注意力被分散，甚至遗忘关键规则。
* **解决方案：高密度极简态势注入**：
  - 提炼为 5~6 行核心态势卡，仅包含：
    1. 当前轮次（如：第 n 轮）
    2. 弹仓状态（剩余实弹/空弹数量）
    3. 双方血量与可用道具列表
    4. 特殊生效状态（如：枪管锯断、被戴上手铐）
    5. 最核心判定：**【当前由谁行动】**
  - **生命周期约束**：该态势注入仅在 `game.status === 'playing'` 时注入，未开始或结束后彻底停止注入。

### 4. 固化玩家先手导致单调机械
* **问题表象**：
  无论何时对弈，默认均为玩家打第一枪或出第一张牌，缺乏真实博弈的随机感与刺激感。
* **解决方案：50% 抛硬币开局 + 轮次交替更迭**：
  - **首轮抛硬币**：开局参数默认 `starter = 'random'`，50% 概率选择 `<user>` 或角色，记录 `firstStarter`；
  - **后续轮次交替**：一轮弹药/手牌打空重新装填时，按照轮次奇偶公式 `(round % 2 === 1) ? firstStarter : otherActor` 自动交替换先手；
  - **跨轮状态重置**：换轮装弹时，上一轮遗留的负面或控制状态（如手铐禁锢 `handcuffed = null`）必须在重装阶段自动清除。

### 5. AI 先手唤醒与动作时序契约
* **问题表象**：
  掷硬币由 AI 先手开局时，界面卡住等待玩家点击；或者疑惑系统是先播报动作还是先发送聊天台词。
* **解决方案：自动唤醒与顶层 JSON 执行契约**：
  - **自动唤醒**：在接受对决（`acceptGame`）后，若判定 `game.turn === 'ai'`，底层直接激活 AI 行动逻辑并触发 `service.continueChat(id)`，实现开局秒级出招；
  - **执行契约时序**：AI 单次生成返回的 JSON 结构中同时包含顶层 `gameAction` 与 `messages` 数组。底层消息调度器保证**先执行 gameAction 状态机结算与系统动作播报**，随后再将 `messages` 渲染为角色的对话气泡，天然保证了“动作判定在先、说话在后”的时序合理性。

## 避坑检查清单 (Sanity Checklist)

- [ ] **是否清除了玩家代发言？** 检查全局代码，确保没有 `service.send(id, '我接受...')` 或任何以玩家名义发送的硬编码台词。
- [ ] **是否去除了括号旁白？** 检查提示词与系统文本，确保聊天气泡中全为纯对话。
- [ ] **多轮对弈中 AI 是否陷入复读？** 测试连续操作 5 轮，确认给 AI 的 `{{latest_user_input}}` 不包含开局时的陈旧用户文本。
- [ ] **AI 出牌失败是否有兜底？** 当 AI 未返回合法 `moveIndex` 或 `notice` 时，引擎应具备随机合规出牌与默认系统公告的降级保护。
- [ ] **状态是否防回滚？** 在 UI 执行异步 API 调用与 `render()` 时，确保内存变量 `ui.activeGame` 不会被过期的 store 快照覆盖。
- [ ] **对弈面板是否遮挡输入框？** 验证抽屉展开与折叠两种状态下，底部 `#sms-draft` 输入框与发送区始终完全可见、可操作。
- [ ] **图标与视觉风格是否统一？** 检查界面与系统公告中没有割裂的彩色系统 Emoji，全量采用单色线性 SVG 图标。
- [ ] **系统消息删除按钮是否低侵入？** 确认系统通知药丸既保留了删除功能，又未引入突兀破坏排版的大按钮（仅 hover/长按时浮现）。
- [ ] **博弈参数是否支持局内直接交互？** 确认牌桌顶栏的赌注等参数可点击唤起原生 `dialog.custom` 弹窗进行双向动态修改。
- [ ] **终局上下文是否配置了过渡缓冲与自动清除？** 检查对战流水是否在终局 5 轮后自动从 Prompt 中静默剥离，避免持续占用 Token。
- [ ] **对决提示词是否消除代词并严格防代打？** 确认 Prompt 中使用 `【<user>】` 与 `【角色】` 客观标识，并在玩家回合明确禁止 AI 代打。
- [ ] **战局提示词是否具备严格生命周期？** 确认对局态势仅在 `status === 'playing'` 时注入，终局后立即停止注入。
- [ ] **先手机制是否支持随机与轮次交替？** 确认首轮支持 50% 抛硬币，重新装填/换轮时交替先手，且上一轮控制状态已清除。
- [ ] **AI 随机先手时是否能自动出招？** 确认接受对决判定 AI 先手时，能直接触发 `continueChat` 自动开枪/出牌，无需玩家手动多余点击。
- [ ] **小游戏图标是否支持点击呼出教程？** 确认抽屉顶栏的小游戏图标为可点击按键，点击能就地唤起/切换规则与道具玩法说明弹层。
- [ ] **界面与文案是否彻底去除了人名括号备注？** 确认无 `【<user>】(旅行者)`、`【角色】(Seraphina)`、`你(玩家)` 等生硬的括号解释，直接叫名字或写 `<user>` / `角色`。
- [ ] **操作与道具下方是否去除了冗余副文案？** 确认按钮与道具栏无“点击立即使用”、“实弹伤害空弹虚惊”等画蛇添足的说明性小字。
- [ ] **选项入口是否为纯中文？** 确认小游戏选择入口、菜单按钮无多余的英文翻译副标题（直接写 `恶魔轮盘`，不写 `恶魔轮盘 Buckshot Roulette`）。
- [ ] **顶栏是否保持单行横排且长赌注优雅截断？** 确认 `X 轮` 标签、赌注药丸与认输按钮横向单行对齐，超长赌注通过省略号隐藏不撑破布局。
- [ ] **终局折叠条文案是否极简？** 确认折叠收拢条文案严格限定为 `恶魔轮盘对决结束 ▾`，无多余说明。
